## 2. Goal and user-observable result

The clickable shell stays the Phase 1 preview. What this commit adds is one scenario that proves the Phase 2 boundary still holds when the steps run together:

- Campaign A’s player is visible to A and invisible to B, while a raw table read still finds the row.
- A stale rename returns `CONFLICT` and does not change the name.
- A command body that inserts a player and then throws returns `ABORTED` and leaves that campaign’s players, revision, and audit rows unchanged.
- A club from the other campaign returns `VALIDATION`. Reusing A’s player id on B returns `DUPLICATE`.
- A stored player that fails Zod makes `getPlayer` throw `CORRUPT`. It does not come back as a player with a zero wage or value.
- After the database is closed and the cache is dropped, A’s renamed name, revision, and player read back.
- A version 2 probe keeps the row written at version 1. `TouchlineDatabase` still declares version 1 only.
- `assertStorageAvailable(undefined)` throws `UNAVAILABLE`.

`pnpm dev` and the production preview still show **Touchline OS** and `Static preview — not save data`. Neither one creates a database named `touchline-os`.

### Public API

`verbatimModuleSyntax` is on. `erasableSyntaxOnly` is on. Do not add TypeScript enums or parameter properties.

```ts
export function assertStorageAvailable(indexedDB: IDBFactory | undefined): void

export function closeDatabaseForTests(name: string): void
```

`assertStorageAvailable` throws `PersistenceError` `UNAVAILABLE` with message `IndexedDB is not available.` when its argument is `undefined`. It does not read the global `indexedDB` and it does not open a database. A defined factory returns normally.

`closeDatabaseForTests` closes the cached `TouchlineDatabase` for that name, if one exists, and removes it from the cache. It does not call `Dexie.delete`. The next `getDatabase(name)` is a new instance and still sees the committed rows.

`TouchlineDatabase` still calls `version(1)` only. `DATABASE_VERSION` stays `1`. Do not add `this.version(2)`.

## 7. Tests to add/change

Campaign A input: ids `campaign-a`, `club-a`, `season-a`, `audit-a`, `action-a`. Name `Riverside`, kind `fictional`, `seed` null, `generatorVersion` null. Club name `Riverside Athletic`, short name `RIV`, colors `#113355` and `#D4A017`, prestige `40`, academy tier `3`, `scoutingRegion` null.

Campaign B input: ids `campaign-b`, `club-b`, `season-b`, `audit-b`, `action-b`. Name `Hilltown`, kind `fictional`, null seed, null generator version. Club name `Hilltown`, short name `HIL`, colors `#224466` and `#88AACC`, prestige `20`, academy tier `2`, `scoutingRegion` null.

Player input for A: `playerId` `player-a`, `clubId` `club-a`, name `Amina Cole`, group `MID`, positions `['CM']`, nationality null, birth date null, reported age `18`, age reference ordinal `1`, `marketValueCents` null, attributes `{ passing: 70 }`, potential null, source `fictional`, `externalSourceId` null, `isNewgen` false. Audit id `audit-player-a`. Action id `action-player-a`. `expectedRevision` is `1` on that first add.

Every later command call uses a new `auditEventId` and `actionId`. The audit `actionId` index is unique.

Assert `result.ok` and, on failure, `result.code`. Do not assert failure message text. Assert `PersistenceError` and `code` for the corrupt read and for `assertStorageAvailable`.

### Campaign scenario

Run these in one `it`:

1. `createCampaign` for A and for B. Both return `ok: true` and revision `1`.
2. `addPlayer` on A. It returns revision `2`. `listPlayers` for B is empty. `getPlayer` for B and `player-a` is `undefined`. `database.players.get` of that id is still defined. The stored `marketValueCents` is `null`.
3. `renameCampaign` on A with `expectedRevision` `1`, name `Stale Name`, audit id `audit-stale-a`, and action id `action-stale-a`. The result is `CONFLICT`. A’s name is still `Riverside`, A’s revision is still `2`, and A’s audit count is unchanged. Count A’s audit rows with `where('campaignId')`, not a full-table filter written as the assertion’s only read.
4. Call `runCommand` with `kind: 'update'`, B’s id, `expectedRevision` `1`, and tables `campaigns`, `players`, and `clubs`. The body inserts a valid player id `player-abort` for B through `insertPlayer`, using club `club-b`, then throws `new Error('stop')`. The result is `ABORTED`. `listPlayers` for B is empty. B’s revision is `1`. B’s audit count is unchanged. This body is not an exported command.
5. `addPlayer` on A with `playerId` `player-cross`, `clubId` `club-b`, and `expectedRevision` `2`. The result is `VALIDATION`. A’s revision is still `2`. `database.players.get` of `player-cross` is `undefined`. The repository still throws `SCOPE`; this test only sees the `VALIDATION` result from `addPlayer`.
6. `addPlayer` on B with `playerId` `player-a`, `clubId` `club-b`, and `expectedRevision` `1`. The result is `DUPLICATE`. `getPlayer` for A and `player-a` still returns `Amina Cole`. B’s revision is still `1`. `listPlayers` for B is empty.
7. `getCampaign` for id `missing` is `undefined`. `renameCampaign` for id `campaign-missing`, with a valid name, `expectedRevision` `0`, and fresh audit ids, returns `NOT_FOUND`. `listCampaigns` still has only A and B.
8. Store a player row for A with id `player-bad`, the same player fields as `player-a`, and no `source`. Use `as unknown as Player`, as `src/test/database.test.ts` does. `marketValueCents` on that raw row is `null`. `getPlayer` for A and `player-bad` throws `CORRUPT`. The call does not resolve to a player, so it cannot come back with a zero wage or a zero value. `getPlayer` for `player-a` still has `marketValueCents` `null`.
9. `renameCampaign` on A with `expectedRevision` `2`, name `Riverside Athletic`, audit id `audit-rename-a`, and action id `action-rename-a`. It returns revision `3`. Then call `closeDatabaseForTests('touchline-os-test')` and `getDatabase('touchline-os-test')`. The new instance is not the instance used above. `getCampaign` returns name `Riverside Athletic` and revision `3`. `getPlayer` for A and `player-a` returns `Amina Cole` with `marketValueCents` `null`.

### Probe and storage

- On a Dexie subclass that is not `TouchlineDatabase`, using the name `touchline-os-migration-probe`, open version 1 with one table whose primary key is `id`. Store `{ id: 'row-1', name: 'kept' }`. Close it. Open a second subclass of the same name that declares version 1 with that same store and version 2 with that same store and an empty `upgrade`. Read `row-1` back as `kept`. Close it and `Dexie.delete('touchline-os-migration-probe')`. `DATABASE_VERSION` is `1`. A `TouchlineDatabase` opened on `touchline-os-test` has `verno` `1`. Do not add version 2 to `TouchlineDatabase`.
- `assertStorageAvailable(undefined)` throws `PersistenceError` `UNAVAILABLE`. Do not delete or replace the fake IndexedDB.

### Failure cases that must keep failing

- `deleteDatabaseForTests` before the reopen deletes the committed rows. Step 9 uses `closeDatabaseForTests`.
- A JavaScript filter over every player can look like isolation. Step 2 also requires the raw `players.get` to find A’s row and the scoped get for B to miss it.
- Catching the thrown error inside the Dexie callback commits `player-abort`. Step 4 forbids that.
- Adding `this.version(2)` to `TouchlineDatabase` fails the version assertion. The probe subclass is the only class that declares version 2.
- Calling `assertStorageAvailable` with the global `indexedDB` does not prove the `undefined` branch. Pass `undefined`.
